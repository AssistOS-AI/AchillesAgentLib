JWT Verification

The jwt/ module verifies short-lived HS256 JSON Web Tokens and refuses a token whose identifier has already been used. An integrating runtime, such as a Router that signs request tokens for agents, imports it from jwt/jwtVerify.mjs or the package root.

Why a token must be remembered for its whole lifetime

A signed request token is meant to authorize exactly one request. The verifier accepts a token from its issue time until its expiry plus a clock-skew allowance, and because time validation works in whole seconds the token remains acceptable until (exp + clockSkewSeconds + 1) * 1000 milliseconds. If the verifier forgot the token identifier (jti) earlier, a captured token could be presented again inside that window. If a full cache forgot older identifiers to make room, a caller could flood the cache with fresh tokens and then replay an old one. verifyJws therefore asks the replay cache to keep each jti for exp * 1000 + clockSkewSeconds * 1000 + REPLAY_RETENTION_MARGIN_MS - now milliseconds, with a margin of 2000 ms, and the memory cache refuses new tokens when it is full instead of evicting live ones.

Verification steps

verifyJws(token, options) reads the clock once, as now when the caller supplies it or Date.now() otherwise, and refuses a non-finite clock or a negative or non-numeric clockSkewSeconds with JWT_TIME_OPTIONS_INVALID. It then checks the signature, the issue and expiry times, the audience and the optional body hash, and checks replay last, so only a validly signed, current token can learn that it was consumed or that a cache is full. verifyInvocationToken applies the same steps, forwards now, and also checks the invocation type, issuer and tool.

The codes are exported as JWT_ERROR_CODES. Errors from outside the module are not rewrapped: a malformed token segment that is not valid JSON raises the parser's SyntaxError, and an error thrown by a caller-supplied replay cache propagates unchanged. A header or payload that is valid JSON but not an object, such as null, raises a TypeError when its fields are read. The token is still rejected, but not every rejection carries the jwtVerify: prefix. Omitting replayCache, or passing null, skips replay protection for tokens that are multi-use by design, but a jti is still required and is still limited to MAX_JTI_LENGTH characters. The limit is checked on the raw claim before it is trimmed, because a trimmed value can be a substring that keeps a much longer padded claim in memory. The signer chooses its jti, so the bound keeps one signer from making each cache entry arbitrarily large. Ploinky's Router and agent issuers mint 22-character identifiers; its relay minter mints 24-character identifiers and uses its own relay cache.

Replay caches

A replay cache preferably implements consume(jti, ttlMs), which checks and records in one call and returns false for a live identifier. A cache may instead implement both seen(jti) and remember(jti, ttlMs). createMemoryReplayCache({ maxSize, now }) provides both forms in one process: maxSize defaults to 2048, invalid values fall back to 2048, an injected now clock controls expiry, and a key that is not a string or is longer than MAX_JTI_LENGTH is refused without being recorded. The cache never stores the caller's string; each entry is keyed by the 43-character base64url SHA-256 digest of the jti, for consume, seen and remember alike. A now that is not a function, or a reading that is not a finite number, is refused with JWT_TIME_OPTIONS_INVALID before any entry is read or removed, because such a reading would make every entry look expired. Each call drops the expired front of the cache, and one full sweep at most once per second reclaims out-of-order expired entries before the cache refuses a new identifier.

The memory cache lives in one process and is cleared when that process restarts, so a token minted just before a restart can be presented again afterwards, and replicas do not share it. A single cache is also shared by everyone who can present a validly signed token; an integrator with several independent signers should give each verified caller its own cache or quota. The complete contract, including these limitations, is DS014-jwt-verification.

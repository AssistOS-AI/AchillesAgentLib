## Introduction

The `jwt/` module gives an integrating runtime, such as a Router that signs short-lived request tokens for agents, one shared way to verify HS256 JSON Web Tokens and to refuse a token that has already been used. A request token is only single-use when the verifier remembers its identifier for as long as the token could still pass time validation, and when a full memory refuses new tokens instead of forgetting live ones. This specification defines that contract so a consuming runtime can rely on it and supply its own [replay cache](wiki.html#definition-replay-cache) when it needs different bounds.

## Core Content

### Public Interface

`jwt/index.mjs` and the package root must export `verifyJws`, `verifyInvocationToken`, `createMemoryReplayCache`, `MAX_TTL_SECONDS` (120), `DEFAULT_CLOCK_SKEW_SECONDS` (30), `REPLAY_RETENTION_MARGIN_MS` (2000), `MAX_JTI_LENGTH` (128) and `JWT_ERROR_CODES`, alongside the signing helpers from `jwtSign.mjs`. `JWT_ERROR_CODES` must be frozen and must contain `replayCacheExhausted: 'JWT_REPLAY_CACHE_EXHAUSTED'`, `replayCacheInvalid: 'JWT_REPLAY_CACHE_INVALID'` and `timeOptionsInvalid: 'JWT_TIME_OPTIONS_INVALID'`. Errors that carry one of these codes expose it as `error.code`. Every other failure detected by the module's own checks, in the verifier or the memory cache, is a plain `Error` whose message starts with `jwtVerify:`. Errors that do not originate in this module propagate unchanged: a `SyntaxError` from parsing a malformed token segment as JSON, and any error thrown by a caller-supplied replay cache, keep their own type, message and code. A header or payload segment that is valid JSON but not an object, such as `null`, is not checked separately and raises a `TypeError` when its fields are read; the token is still rejected, but callers must not rely on the `jwtVerify:` prefix to recognise every rejection.

### Verification Order

`verifyJws(token, options)` must require a `Buffer` secret and must compute `nowMs = Number(now ?? Date.now())` once. A non-finite `nowMs`, or a `clockSkewSeconds` that is not a finite number of at least zero, must be refused with `JWT_TIME_OPTIONS_INVALID`, because a non-numeric value would otherwise disable expiry checks and retain entries forever. Verification must then decode the token, check the HS256 signature, validate `iat` and `exp` against `nowMs` with the skew and `maxTtlSeconds`, check the audience and the optional body hash, and check replay last. Keeping replay last means a consumed, exhausted or quota outcome is observable only to a caller that presented a validly signed, current token. `verifyInvocationToken` must forward `now` to `verifyJws`.

### Replay Retention

Every verified token must carry a `jti` claim of at most `MAX_JTI_LENGTH` (128) characters, measured on the raw claim before trimming, and the trimmed value must not be empty. A longer raw claim must be refused with `jwtVerify: jti too long` before any cache is consulted, and also when no cache is passed. The raw length is the one that counts because a trimmed value can be a substring that keeps the whole padded claim in memory. The signer chooses its `jti`, so without this bound one signer could make each cache entry arbitrarily large. Ploinky's Router and agent issuers mint 22-character identifiers; its relay minter mints 24-character identifiers and verifies them with its own relay cache. When the caller passes a replay cache, the verifier must ask it to keep the `jti` for `ttlMs = max(1, exp * 1000 + clockSkewSeconds * 1000 + REPLAY_RETENTION_MARGIN_MS - nowMs)`. Time validation floors the clock to whole seconds, so a token stays acceptable until `(exp + clockSkewSeconds + 1) * 1000`; the first margin second covers that rounding and the second absorbs a difference between the verifier clock and the cache clock. A replay at any moment the token is still time-valid is therefore refused with `jwtVerify: jti has already been consumed`, and once that window has passed the token is refused as expired.

### Replay Cache Interface

The preferred cache interface is `consume(jti, ttlMs)`, which checks and records in one synchronous call and returns `true` for a new `jti` and `false` for a live one. When `consume` is absent, the cache must implement both `seen(jti)` and `remember(jti, ttlMs)`; the verifier calls `seen` and, when the `jti` is new, `remember`. A cache with neither form must be refused with `JWT_REPLAY_CACHE_INVALID` instead of silently skipping the check. Passing `undefined` or `null` as `replayCache` is the documented opt-out for tokens that are intentionally multi-use within their lifetime; the `jti` is still required.

### Memory Replay Cache

`createMemoryReplayCache({ maxSize = 2048, now = () => Date.now() })` must return `consume`, `seen`, `remember`, `reset` and `size`. `maxSize` must be a positive safe integer; any other value falls back to 2048. An entry is live while its expiry is after `now()`, so the injected clock controls expiry without mocking `Date`. A `now` that is not a function must be refused at construction, and a call whose `now()` reading is not a finite number must be refused before any entry is read or removed, both with `JWT_TIME_OPTIONS_INVALID`; otherwise a `NaN` or infinite reading would make every entry look expired and admit replays. `consume`, `seen` and `remember` must refuse a key that is not a string or is longer than `MAX_JTI_LENGTH` with a `jwtVerify:` error and record nothing. The cache must never store the caller's string: it keys every entry by the SHA-256 digest of the `jti` in base64url form, a fixed 43 characters, and uses the same digest for `consume`, `seen` and `remember` so lookups match. Recording a `jti` keeps the later of its existing live expiry and `now() + max(1, ttlMs)`, so retention never shrinks. `consume` must report a live `jti` as already present before any capacity decision, so a replay at capacity is reported as consumed.

The cache must fail closed. When a new `jti` would exceed `maxSize`, the cache must first reclaim expired entries and, if it is still full, throw `jwtVerify: replay cache capacity exhausted` with `JWT_REPLAY_CACHE_EXHAUSTED` without recording the new `jti` and without evicting a live one. Entries are kept in the order they were last recorded; every call removes the expired prefix of that order, and one full sweep of out-of-order expired entries, at most once per second, runs before a capacity refusal so that sustained flooding is refused in constant time.

### Limitations and Integrator Responsibilities

The memory cache is per process and in memory only. Restarting the process forgets every consumed `jti`, so a token minted shortly before a restart can be presented again within its remaining lifetime, and separate processes or replicas that verify tokens for the same audience do not share replay state. Deployments that need replay protection across restarts or replicas must supply a shared cache that implements the same interface.

A single memory cache is shared by everyone who can present a validly signed token to it. When several independent callers hold signing secrets for the same verifier, one of them can fill the cache and cause refusals for the others; such an integrator should give each verified caller its own cache or quota. Ploinky does this with its own partitioned caches. Even with per-caller quotas, a shared global ceiling remains: enough distinct secret-holding callers flooding at their full quota at the same time can still exhaust it (with Ploinky's default bounds of 16384 entries per caller and 131072 in total, eight such callers suffice), and every caller is then refused until entries expire. This residual is accepted because it fails closed, never open, and holding a signing secret already requires a trusted installation step.
